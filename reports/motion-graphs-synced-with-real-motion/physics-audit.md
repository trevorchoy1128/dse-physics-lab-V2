# 物理核數：motion-graphs-synced-with-real-motion
規格：reference/11_Book2_難點與3D模擬器規格.md「模擬器 7　運動線圖與真實運動同步」（第 384–420 行），並用 §0.2、§0.3 通用規範　數據：10 個運行、100 010 幀（每運行 10 001 幀，dt = 0.001 s）　**第 2 輪**（實作版本 0.2.0，2026-09-05 16:54 重新導出）

核數方法：不讀 model.ts / plan.ts / Scene.tsx。自寫 Node 程式（scratchpad/audit2.js），按規格方程獨立計算每幀的 s、v、a、路程、速率、線下面積、平均速率、平均速度，再與導出數據逐幀比對。
- live 模式：v = u + at，s = ut + ½at²，a = 參數 a；路程 = ∫|v|dt 用解析式（反向時刻 t₀ = −u/a 分段）。
- draw 模式：v(t) 為以 vt 陣列在整數秒為節點的折線，a = 該段斜率；s、路程按每段梯形解析積分（段內過零另分段）。
- t ≥ T 的凍結幀：預期全部讀數（含 a）保持 t = T 的值（第 1 輪 F1 的修正目標）。
- 兩種模式均為解析解，容差取相對誤差 1e-6（分母取 max(1, |預期|)）。
- 五個 random 運行 index.json 內 `mode: null`；導出數據 t = 0 幀 v = u、a = 參數 a，即按 live 模式運行，本核數亦以 live 模式計算（見 §7 第 1 點）。

## 結論
**不通過**：F2（未修正）、F4（新發現，低嚴重度）。F1、F3 已修正並通過。

- F1（已修正）：10/10 運行在 t = T 的幀 a 讀數與加速度箭嘴 = 參數 a（或折線末段斜率），T 之後 5001 幀（T = 5）／1 幀（T = 10）全部讀數與箭嘴凍結不變，0 幀不一致。
- F3（已修正）：scenario-3-end.png v = −16.6 m s⁻¹ 箭嘴約 100 px，箭頭完整在畫布內；a = −9.81 箭嘴約 62 px；兩者比 1.61 ≈ 16.6/9.81 = 1.69，共用同一比例。最大 |v| = 46.05 對應 46.05 × (100/16.6) ≈ 277 px ≈ 軌道闊度 955 px 的 29%，符合「不超過 30%」。

## 6. 守恆量與邊界
- 本模擬無守恆量（外加加速度的運動學）。可核的一致性：area ≡ s（100 010 幀差 0）；∫v dt 對 s 漂移 ≤ 3.4 × 10⁻¹¹ m（10 s）；v² = u² + 2as 漂移 ≤ 4.8 × 10⁻¹⁰。
- a = 0、u = 0（scenario-st-not-path）：10 001 幀全部讀數恰為 0，t = 0 平均速率／平均速度為 0，無 NaN。
- 參數極端（解析估算，數據內無此運行）：u = ±5、a = ±10、T = 20 → |v| ≤ 205 m s⁻¹、|s| ≤ 2100 m；數值上無溢出。random-3（a = 9.68、T = 5）已見 s = 135.6 m、v = 51.3 m s⁻¹ 正常；scenario-3 軌道軸自動放大到 ±200 m（scenario-3-end.png）。
- 隨機負初速、負加速度（random-4：u = −4.66、a = −4.68）：s = −路程全程，速率單調增，無異常。
- 時間窗末端：t ≥ T 後 t、全部八讀數、兩支箭嘴、標籤全部凍結，逐幀比對 0 個不一致；a 保持參數值（F1 已修），畫面不再自相矛盾。
- 箭嘴像素上限：scenario-3（最大 |v| = 46.05）箭嘴被壓到 ≈ 6.0 px 每 m s⁻¹，最長 ≈ 277 px（29% 軌道闊度）；未壓縮的運行（default、scenario-1、scenario-4）基準 ≈ 24 px 每單位。極端 T = 20、a = 10 時最大 |v| = 205，同一規則下 v 箭嘴仍 ≤ 30%，a = 10 箭嘴會壓到 ≈ 14 px，可辨但細小（規格未定，列 §7 第 5 點）。

## 7. 規格待釐清
1. index.json 內五個 random 運行 `mode: null`（第 1 輪 random-2 為 draw，本輪全部按 live 運行）。導出數據本身一致（v(0) = u、a = 參數 a），但 params 記錄不完整，建議導出器把實際生效的 mode 寫入。
2. 驗證條件三「從未反向時位移讀數與路程讀數必須相等」：物體一直向負方向走時 s = −路程（random-4 全程、random-1 反向前 s = −1.895 對 路程 1.895）。本核數以「大小相等」解讀（通過）。建議規格改為「數值上 |s| = 路程」或說明正方向約定。
3. 「由圖生成運動：學生在 v–t 圖上拖曳畫出線段」：實作是每秒一個節點的折線（manifest 已列 beyondSpec）。折線在節點處 a 不連續（scenario-4 於 t ∈ [4, 5) a = −4，其餘 0），a–t 圖會出現垂直跳變，是否可接受待老師定奪。
4. 導出的 plan().scales（velocity = acceleration = 0.25，10 運行全同）與畫面實際像素比例無關：scenario-3 畫面比例 ≈ 6.0 px 每單位，default ≈ 24 px 每單位，兩者相差 4 倍而 scales 相同。若 scales 欄位意在讓核數員核對畫面比例，應輸出實際採用的比例（含上限壓縮後的值）；否則建議在導出格式說明其意義。
5. 箭嘴自動比例規則（基準比例、30% 上限、依最大 |v|/|a| 壓縮）規格未定，由開發端設定；本輪按開發端描述核對通過，建議寫入規格或 manifest.beyondSpec。
6. 截圖流程：`scenario-N-end.png` 依開發端描述應「跳到時間窗末端」，實得 t = 2.00 s（四張皆然）。建議截圖流程直接把 t 設為 T（情境 1、4 需 t = 10 s；情境 3 可取 t = 5 s），並在截圖後核對讀數面板的 t。
7. 播放中的截圖，軌道標籤與面板 s 相差 2–3 個渲染幀（F4）。若確認是截圖工具分兩次擷取 canvas 與 DOM 造成，可在截圖前先暫停以消除；若是應用內兩處讀取不同幀的狀態，應由同一幀的 plan() 供給兩處。
